# Coordination (P4.7h)

`src/argusnet/planning/coordination.py` → `rust/argusnet-planning/src/coordination.rs`.

The last module in P4.7. Three concerns, none of which share state:

| Concern | Reference | Port |
|---|---|---|
| Coordinator election | `CoordinationManager.elect_coordinator` | `CoordinationManager::elect_coordinator` |
| Claimed cells under RF latency | `update_claimed` / `flush_messages` | same names |
| Formation offsets | `formation_offsets` | same name |

The manager stays stateless apart from its policy; the mutable
`SharedMissionState` is owned by the sim loop and passed in, exactly as the
reference arranges it.

## What the fixture pins

`tests/fixtures/coordination.json`, regenerated by
`scripts/capture_coordination_fixture.py`: 14 election cases, 12 message
sequences and 15 formations. The message sequences record the **whole** shared
state after every call — claimed cells and every pending queue, queues in key
order — because every divergence on that path is an ordering divergence and
none of them shows up in the return value.

## Four behaviours reproduced rather than corrected

Each of these reads like a defect. A sim seeded before this port would diverge
if any were "fixed", so they are ported as-is and pinned.

1. **A drone missing from `battery_states` scores a full `1.0`** rather than
   being skipped, so an unknown platform outranks every known one that has
   burned any energy at all. Two fixture cases, one with the unknown drone
   listed first and one last, so a port that merely skipped it would fail on
   both.

2. **Election divides by `max(capacity_wh, 1.0)`**, not by the capacity. Below
   1 Wh the fraction stops being a fraction. This is *not* the same guard as
   `BatteryState::fraction_of`, which tests `<= 0.0`, so the two must not be
   folded into one helper — `capacity_below_one_wh` flips its answer if you do.

3. **The running best starts at `-1.0` while the running id starts at
   `drone_ids[0]`.** When every fraction is below `-1.0` — reachable only from
   a directly-constructed negative `remaining_wh` — no candidate ever clears
   the bar and the first id wins regardless of who holds the most energy.
   `all_below_the_bar` and its reversed twin pin both outcomes.

4. **`update_claimed` reads the latency from the shared state, not the
   policy.** `CoordinationPolicy` carries a `message_latency_steps` of its own
   and nothing on this path consults it. Tidying the two into one field is the
   single most tempting change in the module and it is a behaviour change
   whenever the sim seeds the shared state differently.

## Three orderings that are part of the contract

* **Election keeps the first strictly-better fraction**, so ties go to the
  earliest entry in the list.
* **A drone's due messages are applied in arrival order**, so when several come
  due on the same step the **last** one survives in `claimed_cells`.
* **Queues are never removed.** `flush_messages` writes the remainder back,
  empty list included, so the key set grows monotonically and keeps insertion
  order. `pending` is therefore an insertion-ordered `Vec` of queues, not a
  `HashMap`: a map passes every single-call check and diverges on
  `a_drained_queue_survives_as_an_empty_queue`.

A negative latency is not guarded against and does not deliver early — it
delivers at the next flush, because nothing outside a flush ever applies a
message.

## `FormationMode::Unrecognized` is not defensive padding

The reference matches `formation_mode` against two names and falls through to
an `else` that emits a **zero** offset. So `"none"` returns an empty map and an
unknown string returns a fully-populated map of zeros. Those are not
interchangeable — a caller distinguishing "no formation" from "the formation
put me on the lead's waypoint" sees the difference — so the enum carries an
`Unrecognized(String)` variant rather than collapsing unknown names onto `Off`.
Both `mode/unknown-maps-to-off` and `mode/unknown-maps-to-abreast` are caught.

## The formation fixture needed nine drones, not five

The plausible wrong spelling of the offset arithmetic is folding the factors
into the unit vector one at a time — `((perp * sign) * rank) * spacing` —
instead of forming the whole scalar first, as `perp * (sign * rank * spacing)`
does. Over random headings and spacings those two disagree in the last bit
about a third of the time.

The first version of this fixture used five drones and odd spacings, and
**caught none of it**. Ranks 1 and 2 are powers of two and scale a float
exactly, and a five-drone formation never reaches rank 3. The offsets looked
thoroughly irrational and pinned nothing.

Two things changed as a result, and both matter more than the extra cases:

* The formations go to **nine drones**, reaching ranks 3 and 4.
* `check_discriminating` in the capture script no longer asks whether the
  numbers look non-round — the check that passed while catching nothing. It
  recomputes every offset the wrong way and **refuses to write the fixture**
  unless the two actually disagree, per formation mode. `coordination_parity`
  asserts the same property from the Rust side, so the set cannot silently lose
  its teeth later.

One associativity claim in an earlier draft of the module docs was wrong and is
recorded here so it is not reintroduced: the `* 0.5` in the V arm is **not**
order-sensitive. Halving is exact, so `(rank * spacing) * 0.5` and
`rank * (spacing * 0.5)` are the same number — checked over 200,000 random
inputs with zero disagreements. Only the vector scaling is order-sensitive.

## Verification

- 19 unit tests in the module, 4 parity tests over the fixture.
- **Mutation: 48 of 48 caught, no survivors and nothing claimed as equivalent.**
  This is the first slice in P4.7 with a clean first pass; the module is also
  the simplest — no search, no geometry, no iteration to termination.
  The result is only meaningful because the harness was checked both ways:
  three mutants were confirmed to fail on a **named assertion** rather than a
  compile error (a mutant that does not compile also reports as "caught"), and
  a deliberately equivalent mutant — `Vec::with_capacity` → `Vec::new` — was
  confirmed to **survive**, proving the harness can report one.
  Two of the 48 — `form/abreast-regrouped` and `form/v-regrouped` — survive
  against the five-drone fixture and die only against the nine-drone one;
  the discrimination guard counts exactly two qualifying offsets per mode,
  and counted zero before the change.
- Fixture regenerates byte-identically from the Python reference.

## Not ported

`CoordinationPolicy.elect_coordinator` is carried but never read by the
manager — the reference does not read it either; the sim loop decides whether
to call an election. It is kept rather than dropped so the policy stays a
faithful mirror of the one the sim constructs.
